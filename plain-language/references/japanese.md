# 日本語の原則

日本語を書く、編集する、日本語に翻訳する、または日本語をレビューするときに、
[共通原則](../SKILL.md#principle-index)に加えてこれらの原則を適用する。
共通原則はこの文書の原則より優先する。共通原則の中では、
[SKILL.md](../SKILL.md) が定めるとおり、意味と論理構造の保持を文体より
優先し、文体の中では用語の統一を最優先にする。

想定する読み手は、日本語を母語とし、扱う分野について一定の専門知識を持つ
人である。

生成する文章がやむを得ず原則から外れる場合や、原則同士が衝突する場合は、
モデルの判断を尊重する。判断の基準は共通原則の
[P01](../SKILL.md#p01-preserve-meaning) と
[P04](../SKILL.md#p04-adapt-to-the-reader-and-task) である。

## 文と段落

### J01 主題を保つ

**方針** 段落が何について述べているかを主題とし、各文でその主題を保つ。
主題を保つために態と語順を選び、主題の語を別の語の従属要素にしない。

**理由** 読み手は主題を手がかりに文をつなぐ。文ごとに主題が動くと、
読み手は何についての説明かを組み立て直す。

**例**

> 設定ファイルは起動時に一度だけ読み込まれる。変更した値は、再起動する
> まで反映されない。

2 文目を「サーバーは再起動するまで変更した値を反映しない」と書くと、主題
が設定ファイルからサーバーに移る。

### J02 読みづらい長文は主張を変えずに組み替える

**方針** 論理の筋は通っているが長くて読みづらいと判断した文は、組み替え
てよい。組み替えの前後で、主張、主題、係り受けを変えない。

**理由** 長い文が読みづらいのは、補足が多くて主張が埋もれるからである。
組み替えて主張を取り出すと、文意がはっきりする。

**例**

> 設定ファイルは起動時に読み込まれるが、環境変数が設定されている場合は
> そちらが優先され、両方が未設定の場合は既定値が使われるので、本番環境
> では環境変数で指定する。

主張を一文目に出し、条件を理由として二文目にまとめる。主張と主題は
変わらない。

> 本番環境では環境変数で指定する。設定ファイルは起動時に読み込まれるが、
> 環境変数が設定されていればそちらが優先され、両方が未設定なら既定値が
> 使われるからである。

### J03 接続助詞「が」を逆接と対比に使う

**方針** 接続助詞「が」は、逆接（「再試行したが、失敗した」）と対比
（「既定では設定ファイルを読むが、環境変数があればそちらを優先する」）に
使う。前置きの「が」は、後続の文の役割を示す接続詞や副詞句に置き換える。
単純に文をつなぐだけの「が」は避ける。会話調の文脈で前置きの「が」を残す
かは、モデルが判断する。

**理由** 「が」は逆接、対比、前置き、単純接続を兼ねるが、読み手は
逆接を予想して読み進める。前置きや単純接続の「が」ではその予想が外れ、
読み手は前後の関係を読み直す。前置きの「が」は接続詞と同じ予告の働きを
しているので、接続詞に置き換えると関係が最初から伝わる。

**例**

| 前置きの「が」 | 置き換え |
| --- | --- |
| 補足だが、この設定は次版で廃止される。 | なお、この設定は次版で廃止される。 |
| 結論から言うが、再起動が必要だ。 | 結論から言うと、再起動が必要だ。 |
| 話は変わるが、ログの保持期間を見直したい。 | ところで、ログの保持期間を見直したい。 |

前置きが長いときは二文に分ける。

### J04 因果と逆接を接続詞で示す

**方針** 因果（「そのため」「したがって」）と逆接（「しかし」「ただし」）
は接続詞で明示する。並列と添加（「また」「そして」）は、句点で文が区切ら
れていること自体が役割を果たすので省く。対比、列挙、転換、結論のように
接続詞が係る範囲を示すもの（「一方」「まず」「ところで」「このように」）は
残す。接続詞を例外なく付けることは求めない。

**理由** 接続詞は次の文の読み方を予告する。因果と逆接の接続詞は読み手
の推測に頼らず関係を確定し、並列と添加の接続詞は文の境界が代わりに示せる。
因果を示す接続詞は [P06](../SKILL.md#p06-connect-information) に従い、
根拠がある関係にだけ使う。

**例**

> 設定はサーバー起動時に読み込まれる。そのため、変更を反映するには再起動
> が必要である。再起動中はリクエストを受け付けないが、ヘルスチェックは
> 応答する。

因果の「そのため」と逆接の「が」を残し、3 文目の前に置ける「また」を
省いている。

### J05 読点で係り受けを変えない

**方針** 読点は係り受けを変えない範囲で打つ。打つ位置は、長い修飾語の
境界と、語順を入れ替えて前に出した語の後を基本とし、係り受けが一つにしか
読めない位置には打たない。

**理由** 読点は係り受けを示すと同時に、読み手に処理の負荷をかける。
係り受けを示さない読点は負荷だけを残し、係り先を変える読点は意味を変えて
しまう。

**例**

| 文 | 読点の根拠 |
| --- | --- |
| サーバーはリクエストを検証する。 | 短い文なので打たない。 |
| サーバーは、クライアントが送信したリクエストに含まれるトークンを検証する。 | 「は」と述語の間に長い修飾語があるので、境界に打つ。 |
| 昨日、山田さんはデプロイした。 | 短い修飾語「昨日」を主題より前に出したので打つ。 |

### J06 修飾語を節から長い順に並べる

**方針** 修飾語は、節を先に句を後に、長いものを先に短いものを後に、
大きな状況を先に置く。一つの文に長い連体修飾節を二つ以上入れず、修飾節の
中の語に別の修飾節を付けない。この順序は係り受けを一義にするための手段
であり、係り受けが一義に読める並びなら順序にはこだわらない。

**理由** 日本語では述語が最後に来るため、読み手は修飾語がどの語に係る
かを保留しながら読む。短い修飾語が長い修飾語の前に来ると、係り先を誤り
やすい。修飾節の入れ子は、未完の節を同時に抱えさせる。

**例**

> 厚手の白い横線の引かれた紙

「横線の引かれた」は節、「厚手の」「白い」は句なので、節を先に置く。

> 横線の引かれた厚手の白い紙

### J07 用語を概念で統一する

**方針** 同じ概念には同じ用語を使い、類義語で言い換えない。同じ語が
異なる概念を指すこともある。その語を変えるときは、該当する概念を指す箇所
だけを変え、他の概念を指す箇所は変えない。翻訳では、同じ語の訳語が概念
ごとに異なってよい。

**理由** 語が変わると、読み手は概念も変わったのかを確かめなければなら
ず、読みが止まる。概念が違うのに語形をそろえると、読み手は同じものだと
誤解する。

**例** 同じ概念は同じ語で書く。

> クライアントはリクエストを送信する。サーバーはリクエストを検証する。

2 文目を「サーバーは要求を検証する」と書くと、「要求」が「リクエスト」と
同じものかを読み手が確かめることになる。

同じ語が異なる概念を指すときは、訳語を分ける。

> Run the tests before you run the server.

> サーバーを起動する前に、テストを実行する。

原文の run は、テストの実行とサーバーの起動という別の概念を指している。

## 用語

### J08 英語由来の用語の表記を選ぶ

**方針** 英語由来の用語は、次の優先順で表記を選ぶ。

1. 業界で英字表記が定着している語は英字で書く（Pull Request、API、CI/CD）。
2. 日本語の専門用語やビジネス用語として定着した表記がある語はその表記で
   書く（非同期、可用性、リスク、タスク）。常用漢字表にない字はひらがなに
   開く（べき等）。
3. 広く定着していないがカタカナ表記が許容される語はカタカナで書く
   （デプロイ、ロールバック、オブザーバビリティ）。
4. いずれにも該当しない語は原語で書く。

読み手が実際に目にする表記に合わせ、英語の表現を無理に漢字表現へ置き換え
ない。

**理由** 読み手はドキュメント、コード、GitHub で用語を英字やカタカナ
のまま目にしている。その表記と一致させると、[P02](../SKILL.md#p02-keep-terms-consistent)
の求める用語の同一性が保たれる。常用漢字外の漢語は、読めても書けない語
になりやすい。

**例** 「deploy」は「配備する」ではなく「デプロイする」と書く。
「idempotent」は「冪等」ではなく「べき等」と書く。

### J09 専門用語を使い普及度に応じて補足する

**方針** 専門用語がある概念には、その用語を積極的に使う。読み手の中で
の普及度を、誰でも知っている、聞いたことはあるが意味が曖昧、知らない人が
多い、の三段階で判断し、二段階目以降の語には初出で補足を付ける。段階の
判断は、想定する読み手の知識に照らして
（[P04](../SKILL.md#p04-adapt-to-the-reader-and-task)）モデルが行う。

補足の形は説明の長さで選ぶ。名詞句か短い節で済むなら括弧で添える。動詞、
条件、例を含む説明が必要なら、用語を主題にした別の文で述べる。

**理由** 専門用語は概念を正確に指し、読み手が自分の知識と結び付ける
手がかりになる（[P10](../SKILL.md#p10-respect-technical-meaning)）。
長い補足を括弧に入れると主語と述語が離れ、係り受けが読みにくくなる
（[J06](#j06-修飾語を節から長い順に並べる)）。

**例**

> べき等（繰り返し実行しても結果が同じ）な操作にする。

> この操作は CRDT を使う。CRDT は、複数の複製を独立に更新しても、あとで
> 矛盾なく統合できるデータ構造である。

### J10 略語と造語に原語を併記する

**方針** 略語には、初出で展開形を併記する。造語や、特定の文献や組織の中
だけで使われる用語には、初出で原語を併記する。定着したカタカナ語には併記
しない。

**理由** カタカナ語は読み手が原語を推測できる。略語と造語は綴りを推測
できず、併記がなければ検索の手がかりがない。

**例**

> CRDT（Conflict-free Replicated Data Type）を使う。

> ストラングラーフィグ（strangler fig）パターンで、旧システムを段階的に
> 置き換える。

### J11 固有名詞は定着した表記で書く

**方針** 企業名、製品名、メディア名などの固有名詞は、日本語で定着した
表記があればそれに従い、なければ原語のまま書く。人名はカタカナで書き、
初出で原語の綴りを括弧で添える。

**理由** 読み手は固有名詞を見慣れた形で認識する。見慣れない表記は、同じ
対象だと気づくのを難しくする。綴りの併記は、読み手が検索する手がかりに
なる。

**例**

> マーガレット・ハミルトン（Margaret Hamilton）は、NASA のアポロ計画で
> 宇宙船に搭載するソフトウェアの開発を主導した。

## 文体

### J12 文体を文書の種類に合わせて統一する

**方針** 文体は文書の種類を参考にして選び、一つの文書の中で統一する。
チャットの回答と手順書では「です・ます」体、README、仕様書、設計文書では
「である」体を参考の既定とする。依頼者の文体や既存文書の文体がある
ときはそれに合わせる。文脈が求めるときは、モデルの判断で既定から外れて
よい。

敬語は「〜します」「〜してください」程度を目安にし、相手や場面に合わない
過剰な敬語や婉曲を重ねない。

**理由** 論理的に結論を導く文章には「である」体が向き、読み手に直接
語りかける文章には「です・ます」体が向く。過剰な敬語は文を長くし、伝える
内容を増やさない。

**例** 仕様書では「設定は起動時に読み込まれる。」、手順書では「設定を
変更したら、サーバーを再起動してください。」と書く。

## 表記

### J13 機能語をひらがなで書き常用漢字を基本にする

**方針** 形式名詞、補助動詞、接続詞などの機能語はひらがなで書く。
「こと」「とき」「ため」「ほど」「など」、「〜てください」「〜ていく」、
「できる」「いる」「なる」、「さらに」「ただし」「また」が該当する。
実質的な意味を持つときは漢字で書く（「資格が欲しい」「2 通り」）。

漢字は常用漢字表を基本にする。読み手が一定の専門知識を持つと想定する
ので、その分野で定着した表外字の語は漢字で書く。

**理由** 機能語をひらがなで書くと、漢字で書かれた実質語が視覚的に際立ち、
語の切れ目が分かる。常用漢字表は読み手が共有する基準であり、表外字を
使うかは読み手の知識に照らして判断する。

**例** 「〜する事が出来る」ではなく「〜することができる」と書き、
[P09](../SKILL.md#p09-express-actions-with-verbs) に従って「〜できる」と
縮める。

### J14 漢字の誤変換が疑われる字を直す

**方針** 日常語の中に常用漢字表にない字や、語の意味と合わない字が現れ
たら、誤変換を疑い、辞書にある語形に直す。正しい字に確信が持てないとき
はひらがなに開く。書いた後の点検でも同じ基準で見直す。

**理由** 生成した文章には、同じ読みの別の字が混入することがある。表外
字や意味の合わない字は、その混入を見つける手がかりになる。

**例** 「枡組み」は「枠組み」に直す。「枡」は常用漢字表にない字で、
日常語の「わくぐみ」に現れるのは不自然である。

### J15 カタカナ語の長音を統一する

**方針** 原語の語尾が -er、-or、-ar の語は長音を付ける（サーバー、
ユーザー、コンピューター）。語尾が -y の語は長音を付けない（セキュリティ、
プロパティ、メモリ）。既存文書や製品名に別の表記があるときは、それに合わせて文書
内で統一する。

**理由** 長音の有無は表記のゆれの主な原因であり、ゆれると
[P02](../SKILL.md#p02-keep-terms-consistent) の求める用語の同一性を読み手
が確かめることになる。

**例** 「サーバ」と「サーバー」を一つの文書に混在させない。

### J16 半角と全角を使い分ける

**方針** 数字と英字は半角で書く。半角文字の前後には半角スペースを置く。
ただし、全角の句読点や括弧に接する位置には置かない。記号は係る文字に合わ
せる。日本語の部分に係る記号は全角（「いいね！」の「！」）、数字と英字に
係る記号は半角（「v2.0」の「.」、「3,000」の「,」）で書く。桁区切りは
3 桁ごとに入れる。

**理由** 半角文字の前後のスペースは、日本語の中で英字や数字の境界を
目立たせ、用語を視認しやすくする。記号を係る文字に合わせると、記号が
どちらの部分に属するかが読み手に伝わる。

**例** 「AI は 3 つの API を呼び出す。」と書く。

### J17 箇条書きの形式をそろえる

**方針** 箇条書きの各項目は、短い句か文のどちらかにそろえ、混在させ
ない。短い句とは、体言止めと、「〜を確認する」のように動作を項目名として
示す句を指し、句点を付けない。文とは、主語と述語を備えた完結した文を指し、
句点を付ける。項目が二文以上になるときは文の形にする。項目の文体と詳しさ
もそろえる。

**理由** 形式がそろった項目は、[P08](../SKILL.md#p08-match-form-to-logical-structure)
の求める並列関係を読み手に示す。混在すると、読み手は項目の違いに意味が
あるかを考える。

**例** 短い句でそろえた項目には句点を付けない。

- 設定ファイルを読み込む
- 環境変数を確認する
- 既定値を適用する

文でそろえた項目には句点を付ける。

- 設定ファイルは起動時に一度だけ読み込まれる。
- 環境変数は設定ファイルより優先される。

### J18 段落を空白行で区切る

**方針** 段落は空白行で区切り、行頭を字下げしない。

**理由** Markdown と Web の文章では空白行が段落の区切りとして定着して
おり、行頭の空白は無視されるか意図しない書式になる。
